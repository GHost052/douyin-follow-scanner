# 浏览器依赖说明（实测结论）

> 问题：这个工具能不能**完全不用浏览器**？
> 结论：**不能完全脱离浏览器**，但可以让浏览器**完全隐身**（用户无感）。

---

## 一、实测数据

用同一份登录态，对两个核心接口做了 4 组对照实验：

| 请求方式 | 作品接口 `aweme/post` | 关注列表 `following/list` |
|---|---|---|
| ① 浏览器页面内 `fetch`（不带签名） | ✅ 200，正常返回 21 条 | ✅ 200，正常返回 22 条 |
| ② 纯 Node HTTP + Cookie（不带签名） | ❌ **403** `Blocked by ArgusSecurityPlugin Uifid Not Found` | ❌ 200 但 `status_code=5 参数不合法` |
| ③ 纯 Node HTTP + 完整参数 + **带签名** | ✅ **200，正常返回 21 条** | ✅ **200，正常返回 22 条** |
| ④ 纯 Node HTTP + 完整参数，**去掉签名** | ❌ **403** `Blocked by ArgusSecurityPlugin Sign Invalid` | ✅ 200，正常返回 22 条 |

（"完整参数"指从浏览器真实请求中抓取的 URL，含 `uifid`、`msToken`、`verifyFp`、`fp`、`webid`、`a_bogus` 等指纹参数）

## 二、由此得出的三个事实

1. **纯 HTTP 请求是被允许的** —— 只要带上浏览器生成的完整指纹参数和签名，接口正常返回。这说明 Node 端发请求本身没问题。
2. **作品接口强制校验签名 `a_bogus`** —— 去掉就 403 `Sign Invalid`。该签名由抖音的 `webmssdk` JS 生成，Node 端无法直接产出。
3. **风控是按"请求指纹"决定是否强制签名** —— 在浏览器页面内发同样的请求，不带签名也能过；纯 Node 请求则必须带。因为浏览器请求自带 `sec-ch-ua`、`sec-fetch-*` 等指纹头。

## 三、两个无法绕过的硬依赖

| 依赖 | 说明 | 能否纯 Node 解决 |
|---|---|---|
| **登录** | 扫码登录需要渲染二维码、轮询扫码状态、完成登录跳转 | ❌ 除非让用户手动从自己浏览器导出 Cookie（对小白极不友好） |
| **签名 `a_bogus`** | 作品接口强制校验，由抖音 JS 生成 | ❌ 除非移植整套 webmssdk 算法（工作量大，且抖音一更新就失效） |

## 四、推荐架构：让浏览器"隐身"

既然绕不开，就让用户**完全看不见**它：

```
┌──────────────────────────────────────────────┐
│  界面：本地网页（极简两页界面）                  │
└───────────────┬──────────────────────────────┘
                │ 127.0.0.1
┌───────────────▼──────────────────────────────┐
│  Node 服务：扫描编排 / 数据 / 报告             │
└───────────────┬──────────────────────────────┘
                │
┌───────────────▼──────────────────────────────┐
│  后台 headless 浏览器（无窗口、无界面）         │
│  只负责：维护登录态 + 发接口请求                │
│  使用系统 Edge/Chrome 的 headless 模式          │
│  → 不下载 Chromium，零额外体积                  │
└──────────────────────────────────────────────┘
```

**好处**：
- 用户全程看不到任何浏览器窗口，体验就是"一个桌面应用"
- 复用系统已装的 Edge/Chrome 的 headless 模式，**不增加打包体积**
- 解决了当前"不要关闭浏览器窗口"的体验问题

**代价**：
- 首次登录仍需弹出一次窗口扫码（之后可全部 headless）

## 五、结论

| 方案 | 可行性 | 评价 |
|---|---|---|
| 完全不用浏览器 | ❌ 不可行 | 登录与签名两个硬依赖无法绕开 |
| 纯 HTTP + 用户手动导出 Cookie + 自研签名算法 | ⚠️ 技术上勉强可行 | 用户门槛高、算法易失效、维护成本大，**不推荐** |
| **headless 后台浏览器（推荐）** | ✅ 可行 | 用户无感、体积不增加、稳定性与现在一致 |
